# Production-запуск WedFotoBook на VPS

## Схема

nginx завершает HTTPS и проксирует запросы на Next.js, слушающий только `127.0.0.1:3000`.
Приложение работает как Node.js-процесс под PM2. SQLite-файл лежит в постоянном каталоге
вне checkout, например `/var/lib/wedfotobook/wedfotobook.sqlite3`.

## Переменные

В `.env.local` нужно задать:

- `DATABASE_PATH` — абсолютный путь к SQLite;
- `CONTACT_MAILER_URL=http://127.0.0.1:3081/send` и длинный `CONTACT_MAILER_TOKEN`;
- `CONTACT_TO_EMAIL` и `CONTACT_FROM_EMAIL`;
- `ADMIN_PASSWORD_HASH`, `ADMIN_SESSION_SECRET`, `ADMIN_LOGIN_SALT`, `ADMIN_AUDIT_SALT`;
- `RATE_LIMIT_SALT`;
- `TRUST_PROXY_ORIGIN=1` только если nginx всегда перезаписывает `Host`, `X-Forwarded-Host` и `X-Forwarded-Proto`.

Реальные секреты нельзя печатать в логи или хранить в Git. Файл `.env.local` должен иметь права `600`.

## Сборка и запуск

```bash
npm ci
npm run lint
npm run build
npm run check:contact-config
npm run db:migrate
pm2 start npm --name website -- run start:vps
pm2 save
```

При обновлении **не выполняйте `npm ci` и `npm run build` в каталоге работающего процесса**:
сборка удаляет/заменяет файлы, которые ещё обслуживает текущий релиз. Не останавливайте PM2 на время подготовки.
Создайте отдельный каталог релиза с зависимостями и `.env.local` (права `600`), затем в нём выполните:

```bash
npm ci
npm run lint
npm run build
npm run check:contact-config
npm run db:migrate
```

Запустите подготовленный релиз на резервном loopback-порту, проверьте `/`, JavaScript и `/api/health/`.
Только после успешных проверок переключите nginx на этот процесс (`nginx -t` перед reload),
сохраните конфигурацию PM2 и затем завершите старый процесс. Держите предыдущий релиз для отката.
Не переносите Windows CRLF в shell-скрипты: `.gitattributes` фиксирует LF; перед активацией выполните
`bash -n scripts/start-vps.sh` и проверку отсутствия `\r`.
Все операции переключения выполняйте под `flock /root/wedfotobook-update.lock ...`:
это исключает параллельные выкладки и автоматическое восстановление во время переключения.

`start:vps` сам повторно проверяет конфигурацию, применяет миграции и запускает готовую сборку.

## Контроль доступности

`https://wedfotobook.ru/status/` обслуживается nginx отдельно от Node.js. Показывает последние
1440 проверок, время, задержку и неработающие компоненты. Данные старше 150 секунд отмечаются как неизвестное
состояние, а не как работающий сайт. Процент — доля успешных **проверок**, не гарантированное время uptime.

`wedfotobook-monitor.timer` каждую минуту запускает `scripts/uptime-monitor.py` через отдельный systemd oneshot.
Проверяются HTTPS главной страницы, JavaScript, `/api/health/` (готовность страницы и чтение таблицы заявок)
и локальный health endpoint. Это не проверка записи заявки, доставки письма или всех пользовательских сценариев.
При трёх локальных сбоях подряд выполняется `pm2 restart website`, не чаще одного раза в 10 минут;
блокировка выкладки предотвращает вмешательство. Сбой только внешнего HTTPS не вызывает перезапуск приложения.

История за 90 дней: `/var/lib/wedfotobook-monitor/history.sqlite3`. Публичный JSON не содержит данных заявок,
секретов или текстов серверных ошибок. HTML/JSON: `/var/www/wedfotobook-status/`.
Исполняемый скрипт: `/opt/wedfotobook-monitor/uptime-monitor.py`; unit-файлы хранятся в `scripts/monitoring/`.

```bash
systemctl status wedfotobook-monitor.timer
journalctl -u wedfotobook-monitor.service --since today
curl --fail https://wedfotobook.ru/api/health/
```

Монитор работает на том же VPS: при остановке всего сервера история содержит пропуск наблюдений,
страница статуса тоже недоступна. Для независимого контроля питания/сети VPS нужен внешний монитор,
проверяющий HTTPS и health endpoint с другого сервера. Не считать пропуски успешными проверками.

### Почтовые уведомления

Получатель и отправитель задаются отдельно от заявок в `/etc/wedfotobook-monitor.env` (root, права `600`):

```ini
UPTIME_MAIL_TO=owner@example.com
UPTIME_MAIL_FROM=WedFotoBook <orders@fotobooktest24.ru>
```

Укажите подтверждённого получателя и настроенного отправителя. Без корректных адресов отправка не выполняется.
После изменения env-файла следующий запуск systemd сам прочитает новые значения.
После двух последовательных неудачных проверок создаётся одно письмо о сбое; после первой успешной
проверки — письмо о восстановлении. Одиночный сбой письма не вызывает. Письмо содержит время UTC,
HTTP-коды, задержки, результат автовосстановления в этой проверке и вероятную причину.
DNS, TLS, отказ соединения и тайм-аут различаются; HTTP 503 готовности не выдаётся за доказанный сбой БД.

Уведомления сохраняются в таблице `outbox` базы мониторинга до передачи локальному Postfix через sendmail.
При ошибке передачи следующая проверка повторяет попытку; восстановление отправляется после сообщения о сбое.
Успешная передача в Postfix не доказывает доставку адресату: проверяйте очередь и журнал почтового сервера.
При аварии между передачей письма и фиксацией результата возможен повтор с тем же Message-ID.
При полном отключении VPS или его сети немедленная отправка невозможна — для этого нужен внешний монитор.

## Собственная почта

На Ubuntu один раз выполните:

```bash
sudo npm run setup:local-mailer
```

Установщик создаёт отдельного непривилегированного пользователя, loopback-only службу,
Postfix, OpenDKIM и случайный токен. Приложение не может передать токен на внешний адрес.

Для доставляемости нужны DNS-записи SPF, DKIM и DMARC, а также PTR IP-адреса на `mail.fotobooktest24.ru`.
Статус `notification_status=sent` означает, что Postfix принял письмо. Окончательную доставку проверяют по
`postqueue -p`, журналу Postfix и фактическому появлению письма у получателя.

## Reverse proxy

Порт 3000 не публикуется во внешнюю сеть. nginx должен:

- перенаправлять HTTP на HTTPS;
- передавать исходный `Host` и перезаписывать forwarded-заголовки;
- не кешировать `/admin/` и `/api/`;
- ограничивать тело API-запросов;
- не писать в логи тела запросов, cookies и авторизационные заголовки.

## Проверка после запуска

```bash
npm run check:assets -- --base-url=https://fotobooktest24.ru --report=tmp/assets-live.json
curl -sSI https://fotobooktest24.ru/
curl -sSI https://fotobooktest24.ru/admin/
curl -sS -o /dev/null -w 'TTFB: %{time_starttransfer}s Total: %{time_total}s\n' https://fotobooktest24.ru/
postqueue -p
```

Дополнительно проверьте вход в `/admin/`, создание заявки, её запись в SQLite и почтовый ответ
получающего сервера. Перед каждым релизом создавайте резервную копию SQLite и проверяйте число ключевых
записей до переключения.
